# Fixtures

## Read this before using anything in here in a demo

**Everything under `synthetic-checkout/` was written by hand. It is not a
recorded agent session, and the mismatch in it was not found — it was authored.**

B-R26 says: *never plant a bug and present it as found.* A checker tuned to a bug
you seeded measures nothing. These fixtures exist to exercise the code paths and
to make the test suite meaningful. They are **not** evidence that the premise
holds, and they must never appear on stage.

Both fixture directories carry a `SYNTHETIC` marker file. `tools/demo.py` refuses
to run against a directory containing that marker unless `--synthetic-ok` is
passed, and prints a banner saying so when it is. That refusal is the enforcement
mechanism for B-R26 — not a convention, a check.

## Gate B is unresolved

BUILD-PLAN days 1-2 require three genuine mismatches reproduced from a real
recorded session, documented in `findings/reproduced.md`. That file does not
exist yet, because no recorded session exists yet. Until it does:

- the premise is unproven,
- no number from these fixtures is publishable,
- and per the build plan's own wording, zero reproduced mismatches means **stop**,
  not "build anyway and see".

What is in this repository is the machinery. What is missing is the evidence.

## What each fixture is for

| Path | Purpose |
|---|---|
| `synthetic-checkout/` | Exercises every finding class: payload mismatch (encoding), payload mismatch (field names), env var read but never set, and a zero-caller endpoint. |
| `clean-checkout/` | The same application with the two sides agreeing. Used to assert B-R20: a clean tree produces zero findings. If this ever produces a finding, the checker has a false positive and the checker is wrong, not the fixture. |
| `session.jsonl` | A replayable event log generated by `tools/record_fixture.py` from `synthetic-checkout/`. Regenerate it rather than editing it. |

## The shape of the authored mismatch

It mirrors PRD-A section 2.1 deliberately, because that is the example the
product is specified around:

- producer declares `POST /api/checkout` taking JSON `{email: str, amount: int}`
- consumer sends `multipart/form-data` with `user_email` and `total`

Both halves are internally consistent. Each compiles. Neither is wrong about
itself. That is the whole point of the class.
